# 并发控制

## 模型并发

当上游服务商无法继续接受请求时，它可能返回 HTTP **429（Too Many Requests）**

发生此错误即会进入熔断+回退机制。

## 网关并发

上游返回 429 解决不了**网关自身同时承接过多请求**的问题。

生产环境通常有多个 LiteLLM 实例，每个实例又可能有多个 worker。可以在生产环境的 LiteLLM **YAML 配置文件**中加入入口并发控制：

```yaml
general_settings:
  max_in_flight_requests_per_worker: 64
  max_queued_requests_per_worker: 64
  admission_queue_timeout_seconds: 1.0
```

这三个值取自 LiteLLM 官方文档的**示例配置**，可以作为压测起点，不是所有环境通用的固定值：

- `max_in_flight_requests_per_worker: 64`：每个 worker 最多同时处理 **64** 个请求。先用 64 做压测起点，再根据 worker 的 CPU、内存和响应延迟调整；流式请求要一直占用名额，直到响应结束。
- `max_queued_requests_per_worker: 64`：每个 worker 最多允许 **64** 个请求等待。先设为与处理名额相同，避免高峰时无限积压；如果短时突发经常把队列打满，再结合扩容和压测结果调整。
- `admission_queue_timeout_seconds: 1.0`：请求最多排队 **1 秒**。等不到名额，或队列已经满了，就返回 **503 Service Unavailable**，让调用方稍后重试；不要靠长时间排队掩盖网关容量不足。

### 最佳实践

生产集群中**每个 Pod 运行一个 worker，通过增加 Pod 副本扩容**。上述名额和队列都按 worker 计算：例如 4 个 Pod、每个 Pod 1 个 worker 时，`64` 表示集群理论上最多同时处理 `4 × 64 = 256` 个请求，而不是整个集群总共 64 个。上线前用真实请求压测；上线后观察 `/health/backlog` 中的排队和拒绝数量。持续出现排队超时，应增加副本或优化处理能力，再重新校准这三个值。

参考：[LiteLLM Server Tuning：Per-worker admission control](https://docs.litellm.ai/docs/proxy/server_tuning)。
