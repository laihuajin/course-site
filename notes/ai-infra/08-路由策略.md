# 路由策略

当一个模型组下有多个 Deployment 时，LiteLLM Router 需要决定本次请求交给哪一个。

路由策略有多种供选择：

- `simple-shuffle`（默认）

  从可用 Deployment 中随机挑选；如果配置了 RPM、TPM 或 `weight`，则会按相应权重分配流量。
  
  实现简单、选择开销低，适合作为日常默认策略。
- `least-busy`

  选择当前正在处理的请求数最少的 Deployment。
- `usage-based-routing`（已弃用）

  按当前分钟的 TPM 使用量，优先选择用量较低的 Deployment；配置了 RPM/TPM 上限时也会据此排除超限候选。旧版实现，不建议新配置继续选择它。
- `latency-based-routing`

  记录近期请求的响应耗时，优先选择历史延迟较低的 Deployment。适合候选 Deployment 的延迟差异明显、且有足够历史请求可供判断的场景；历史延迟不能保证下一次请求的耗时。
- `cost-based-routing`

  优先选择价格最低的可用 Deployment。适合多个满足同一业务需求的候选模型或供应商之间做成本优化；先核对模型价格或自定义输入、输出价格，否则选择依据可能不符合实际费用。
- `usage-based-routing-v2`

  用异步方式跟踪各 Deployment 当分钟的 TPM/RPM 使用情况，排除会超过已配置限额的候选，再优先选择 TPM 用量较低的 Deployment。适合确实需要按配额分流的场景。
  
  用量跟踪会增加路由开销。
- `lar1`

  这是为特定 Agent 工作流准备的策略，普通的多密钥负载均衡不需要选它。

  这里不做过多解释，有兴趣的同学自行询问AI。
